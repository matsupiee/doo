# 通知で気づく

> ステータス: 仕様のみ。`notification` テーブルはまだスキーマに無い。
> テーブルの追加とマイグレーション生成は別 PR で行う。API・UI はそのあと。

## ストーリー

ユーザーとして、自分に関係することが起きたら気づきたい。
そうすれば、自分のやりたいことに乗ってくれた人や、自分を入れてくれた達成を見逃さない。

## 動作確認の手順

1. `bun run db:seed` でシードを流す。
2. 別のユーザーで、自分が登録した「やりたいこと」に参加する。
   - 作成者の通知一覧に `mission_participated` が1件届く。
   - 未読があるので、バッジが出る。
   - 通知には誰が起こしたか（actor）と、どこで起きたかが入る。
3. その通知をタップする。
   - もとになった「やりたいこと」の画面に飛ぶ。
   - 既読になり、バッジが減る。
4. 別のユーザーの共同達成に、自分が一緒に達成した人として入れられる。
   - `completion_participated` が届く。
   - その「やりたいこと」に参加していなくて自動で参加者にされた場合も、同じように届く。
   - 知らないうちに参加者一覧に載るので、ここで気づける。
5. 自分の投稿に、別のユーザーがリアクションする。
   - `post_reacted` が届く。
   - リアクションを外しても通知は消えない。起きた出来事の記録として残す。
6. 自分の投稿に自分でリアクションする。
   - 通知は増えない。自分の操作で自分に通知は作らない。
   - 「やりたいこと」を作って自分が参加者になったときも、自分には通知しない。
7. 通知のもとになった「やりたいこと」・投稿・達成を消す。
   - その通知も消える。

## データの持ち方

- 通知は `notification` に1行作る。1テーブル1ファイルの規約どおり
  `packages/db/src/schema/notification.ts` に置く。
  - `user_id` は受け取る人。cascade。
  - `actor_id` は起こした人。cascade。
  - `type` は下の3種類。取りうる値が固定なので enum で持つ。
  - `mission_id` / `completion_id` / `post_id` は飛び先。種別によって使う列が違うので nullable。
  - `read_at` は既読の時刻。null なら未読。
- 通知の種別は3つ。

  | 種別                      | 受け取る人           | きっかけ                           |
  | ------------------------- | -------------------- | ---------------------------------- |
  | `mission_participated`    | やりたいことの作成者 | 誰かがそのやりたいことに参加した   |
  | `completion_participated` | 達成に含められた人   | 自分が共同達成の参加者に入れられた |
  | `post_reacted`            | 投稿の作者           | 自分の投稿にリアクションが付いた   |

- 一覧を引くために `(user_id, created_at)` に索引を張る。
- 飛び先の FK はすべて cascade にする。
  - 参照先が消えたときに、通知も一緒に消える。
- 通知の作成は、きっかけになった操作と同じトランザクションで行う。
  - 参加、達成の記録、リアクションのそれぞれ。
- 送信手段はアプリ内の通知一覧だけ。プッシュ通知とメールは範囲外。
  - 画面の置き場所（タブを増やすか、ホームのヘッダーに出すか）は実装時に決める。
