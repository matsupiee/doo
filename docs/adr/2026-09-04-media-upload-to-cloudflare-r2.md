# 写真・動画のアップロード先に Cloudflare R2 + presigned PUT を使う

- 日付: 2026-09-04
- ステータス: 承認

## 背景

達成の証明（写真・動画）は「URL を手で貼る」しかなく、アップロード基盤が無かった。
本文の実体をどこに置き、どの経路でアップロードするかを決める必要がある。

## 決定

- 保存先は **Cloudflare R2**。設定は `packages/storage`（`@doo/storage`）に閉じ込める。
- アップロードは **クライアントから R2 への直 PUT**。
  API サーバーは `upload.createUploadUrl` で有効期限 5 分の presigned URL を返すだけで、
  バイト列は経由しない。
- 公開 URL（`R2_PUBLIC_BASE_URL` + キー）だけを `post.media_url` に保存する。
  スキーマ変更は不要。
- オブジェクトキーは `posts/{userId}/{cuid2}.{ext}`。
  `userId` は**セッションから取る**（クライアント入力ではない）。
- R2 の環境変数は **任意**。未設定でもサーバーは起動し、アップロードだけが
  `PRECONDITION_FAILED` になる。

## 理由

- 直 PUT なら 100MB の動画が API サーバーのメモリと帯域を通らない。
  Bun のサーバーを大きくせずに済む。
- 署名に `Content-Type` を含めているので、許可リスト外の形式は R2 が拒否する
  （aws4fetch はデフォルトで content-type を署名しないため `allHeaders: true` が必要）。
- キーに cuid2 を入れることで、バケットを公開しても
  `posts/{userId}/` を総当たりして他人の投稿を拾えない。
- 環境変数を任意にすることで、R2 を持たない開発者でも `bun run dev` が通る。

## 却下した選択肢

- **API サーバー経由のプロキシアップロード**（multipart を Hono で受けて R2 に転送）:
  バケットの CORS 設定が要らず、バイト列をサーバー側で検証できる利点はあるが、
  動画で API サーバーの帯域とメモリを食う。React Native からの直 PUT は
  ブラウザではないので CORS の制約も受けない。
- **UploadThing などの外部サービス**: 依存とコストが増える割に、
  すでに Cloudflare を使う前提なら得るものが少ない。
- **base64 を tRPC の入力に載せる**: ペイロードが 1.33 倍になり、
  大きなファイルで現実的でない。

## 影響

- `apps/server/.env` に `R2_*` を追加する（未設定ならアップロード機能のみ無効）。
- バケットは公開読み取りにする必要がある（r2.dev かカスタムドメイン）。
  非公開にしたい場合は、配信側も presigned GET に変える必要がある。
- **サイズ上限はクライアント申告ベース**。presigned PUT では `Content-Length` を
  署名に含めない限り実バイト数を強制できないため、
  上限（写真 10MB / 動画 100MB）は入力検証に留まる。
  厳密に縛る必要が出たら、R2 側のライフサイクル／Worker での検証を足す。
