# 「一緒にやろう」の誘いを assignment 行で表す

- 日付: 2026-09-07
- ステータス: 採用（スキーマのみ先行、API/UI は後続 PR）

## 背景

他の人のミッションを見て「これ一緒にやらない？」と声をかけられるようにしたい。
声のかかり方は2方向ある。

- **誘う (push)**: 自分がやっているミッションに相手を呼ぶ。相手には諾否がある。
- **混ぜて (pull)**: 他人のミッションを見て、自分から参加する。相手の承認は求めない。

既存の `assignment` は「ある人のミッション1件分の状態」を表しており、
`status = "pending"` の行はすでに「渡されたが、まだやっていない」＝お誘いそのものである。
`decline` (`packages/api/src/routers/mission.ts`) で断る導線も実装済み。

## 決定

専用の招待テーブルは作らず、**誘い・参加ともに `assignment` の行として表す**。
スキーマの変更は次の2点だけ。

1. `assignment.picked_by` の enum に `"joined"` を追加する。
   自分から他人のミッションに乗った参加を、`"self"`（自分で作って自分でやる）や
   `"nominated"`（指名された）と区別してバッジ表示するため。
2. `assignment.invite_message` (nullable text) を追加する。
   「これ一緒にやらない？」の一言を添えるためのもの。自分で受けた場合は null。

後続 PR で載せる API の形は次を想定している。

- **誘う**: 既存の `mission.assign` の権限を「ミッションの作成者のみ」から
  「そのミッションの assignment を持っている参加者」へ緩める。リレーのミッションを弾く
  ガードは残す（リレーはクリアした人がバトンを渡す仕組みなので、横入りさせない）。
- **混ぜて**: `mission.join` を新設し、`picked_by = "joined"` の pending 行を自分で作る。
- **参加者の表示**: `mission.participants` で「いま誰がやっているか」を返す。

`(mission_id, assignee_id)` の unique index (`assignment_mission_assignee_uidx`) が
そのまま二重招待・二重参加のガードになる。

一度断られたミッションに再度声をかける場合は、insert ではなく既存の `declined` 行を
`pending` に戻す update として実装する（unique index に阻まれるため）。

## 理由

- 「pending の assignment ＝ 未応諾のお誘い」という既存の意味づけをそのまま使えるので、
  受信箱・断る・クリアして投稿する導線をすべて再利用できる。追加コードが最も少ない。
- 招待を別テーブルに分けると、承諾時に assignment へ移し替える処理が必要になり、
  「誘われている」状態と「やっている」状態が2箇所に散る。
- unique index による重複防止を DB に任せられる。

## 却下した選択肢

- **`mission_invite` テーブルを新設する**: 招待と参加が別テーブルに分かれ、承諾時の
  移し替えと二重管理が発生する。招待に対して「既読」「期限」「複数回の再送履歴」などを
  持ちたくなったら再検討する。今回は1行1状態で足りる。
- **pull（混ぜて）にも相手の承認を必須にする**: 参加のハードルが上がり、
  「見かけたから乗る」という体験が死ぬ。相手のミッションの公開範囲で制御するほうが素直。
- **`picked_by` を増やさず `"self"` を流用する**: 自分で立てたミッションと、
  他人のミッションに乗ったものが区別できず、バッジ表示ができない。

## 影響

- マイグレーション `0002_ambitious_arachne.sql` を追加（`invite_message` カラムの追加のみ）。
  `picked_by` は Drizzle の text enum なので SQL 上の変更は発生せず、型でのみ制約される。
  既存行は `invite_message = null` になる。
- `picked_by` の union が広がるため、native 側のラベルマップ3箇所
  （プロフィール / リレー詳細 / 投稿カード）に `joined` のラベルを追加した。
- API・UI は本 PR では変更していない。後続で `mission.assign` の権限緩和、`mission.join`、
  `mission.participants` を実装する。

## 積み残し（後続で決める）

- **通知がない**: notification テーブルが無いため、誘われたことに気づける場所は
  プロフィールの pending 一覧だけ。誘い機能を出すなら受信箱の設計とセットで考える必要がある。
- **誘い放題になる**: フォロー関係が無く `user.search` で全ユーザーが引けるので、
  権限を緩めると誰でも誰にでも誘いを飛ばせる。招待の上限か、相互フォローの導入を検討する。
- **ミッションの公開範囲**: 他人のミッションを見て声をかける以上、未達成のミッションが
  公開される。項目ごとの非公開フラグが要るかは未決。
