# ドキュメントの書き方

`docs/` 配下の Markdown（ADR・ユーザーストーリー・ルール）に適用する。

## 太字・斜体で強調しない (CRITICAL)

`**強調**` と `*強調*` は使わない。文中に記号が挟まって読みにくくなるため。

```md
<!-- ✅ CORRECT: 文の組み立てで大事なところを示す -->
- 達成を記録すると、必ず投稿が1件作られる。投稿のない達成は存在しない。
- 同じ人を同じ達成に二重には入れられない。

<!-- ❌ WRONG: 記号で強調する -->
- 達成を記録すると **必ず投稿が1件作られる**。投稿のない達成は存在しない。
- **同じ人を同じ達成に二重には入れられない。**
```

強調したいときは、記号ではなく次のどれかで示す。

- 言い切る。条件や例外は次の文に分けて書く
- 箇条書きの1項目として独立させる
- 見出しを立てて section にする
- 表にして並べる

## 記号を使ってよい場面

- コード・テーブル名・カラム名・パス・コマンドはインラインコード（`` `mission_participant` ``）
- 引用（`>`）、見出し（`#`）、箇条書き（`-`）、表、コードブロックは通常どおり使う

## ユーザーストーリーの構成

`docs/user-stories/` の1ファイルは次の順に書く。「受け入れ条件」のセクションは作らない。
条件は動作確認の手順のなかに、そのとき何が起きるかとして入れ子で書く。

```md
# タイトル

> ステータス: どこまで実装されているか

## ストーリー

誰として、何がしたくて、そうすると何がうれしいか。

## 動作確認の手順

1. 手順を番号で書く。
   - その手順で満たすべき条件を、入れ子の箇条書きで書く。
   - 関連するストーリーへのリンクもここに置く。
   - → [別のストーリー](./other-story.md)
2. 次の手順。
   - 条件。

## データの持ち方

- テーブルや列の役割を親の項目に書く。
  - 制約や理由は入れ子で書く。

## 対応するテスト

どのテストがこのストーリーを守るか。

## 関連

- 関係する ADR や他のストーリーへのリンク。
```

- 手順は上から順に実行できる並びにする。前の手順の結果を次の手順が使う。
- 条件は「〜できる」「〜されない」と、確かめられる形で書く。
- 実装が後続のストーリーは、ステータスと動作確認の手順の冒頭でその旨を明示する。

## 1行の長さ

読みやすさのために、日本語の文は 90 桁あたりで折り返す。表とリンクは折り返さない。
